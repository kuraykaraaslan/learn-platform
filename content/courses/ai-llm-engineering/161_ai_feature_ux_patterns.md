## What It Is
An AI feature's backend correctness — a well-validated prompt, a fast model, a solid fallback — is wasted if the interface around it misrepresents what's happening to the user, and the single most important rule is disclosure: users must always know when they're looking at AI-generated content, never content presented as if a human wrote it. This isn't just good practice, it's often a legal transparency obligation for customer-facing chat and generated content (see the AI Data Privacy and Regulatory Compliance lesson), and it's cheap to satisfy — a visible "Generated by AI" badge that doesn't require scrolling to see. The same honesty principle extends to failure and uncertainty: when a model expresses doubt in its own output ("I'm not sure", "you may want to verify"), that signal should surface to the user, not get silently stripped out because it looks unpolished — suppressing it converts a useful hedge into false confidence.

Latency is the second core UX problem, because LLM responses routinely take one to ten seconds, which is long enough to feel broken if the interface shows nothing. A blank area while the model works is always wrong; a skeleton or spinner is the minimum bar, and for anything that streams, a blinking cursor at the end of the growing text is the standard signal that generation is still active — removed the moment the stream completes, at which point the disclosure label appears. Error states deserve the same specificity as loading states: a generic "something went wrong" tells the user nothing actionable, whereas a small fixed set of messages mapped by error code — unavailable, too long, content policy — tells them what actually happened and, where relevant, what to do about it. A visible way to regenerate matters too, because users intuitively understand that AI output varies run to run and will expect a retry option rather than being stuck with one draft.

The last discipline is treating AI output as a draft, not a final artifact, whenever it feeds into something the user will send, publish, or submit — an email reply, a support response, a form fill. The interface must let the user see and edit that content before it goes anywhere, and it must never auto-submit on the user's behalf; the same rule applies to pre-filling a form with AI output as the default state without making it obvious that's what happened. Accessibility is not a separate concern layered on afterward: the loading state needs `aria-live="polite"` so screen readers announce it, error banners need `role="alert"`, and streaming text must never cause keyboard focus to jump mid-generation, which would silently break a screen-reader user's flow through the page. None of these are exotic requirements — they're the ordinary UI craftsmanship every interface needs, applied specifically to the ways an AI feature's behavior differs from a normal synchronous form submission.

## Key Concepts
- **AI disclosure label is mandatory, always visible**: "Generated by AI" or equivalent, without requiring the user to scroll to see it
- **Never present AI output as human-authored**: this applies doubly to contexts easily mistaken for authentic human content — testimonials, reviews, legal or medical text
- **No blank loading states**: a skeleton or spinner is the floor for any AI call taking more than an instant
- **Streaming cursor while active, disclosure label on completion**: the cursor signals "still generating"; removing it and showing the label signals "done, and AI-made"
- **Editable draft, never auto-submit**: any AI output feeding an email, message, or form must be reviewable and editable by the user before it's sent anywhere
- **Specific errors over generic ones**: map error codes to a small fixed set of actionable messages instead of one catch-all "something went wrong"
- **Surface the model's own expressed uncertainty**: don't strip hedging language like "I'm not sure" — it's a real signal the user should see
- **Accessibility is not optional**: `aria-live="polite"` on loading/streaming containers, `role="alert"` on errors, and no focus jumps during a stream

## Example Code
```tsx
// components/AiOutput.tsx — disclosure label, always visible
export function AiOutput({ content, source }: { content: string; source: 'ai' | 'fallback' }) {
  return (
    <div className="ai-output" aria-live="polite" aria-label="AI response">
      {source === 'ai' && <span className="ai-badge">Generated by AI</span>}
      <p>{content}</p>
    </div>
  );
}

// components/AiDraftEditor.tsx — draft pattern, never auto-submit
function AiDraftEditor({ initialDraft, onSend }: { initialDraft: string; onSend: (text: string) => void }) {
  const [value, setValue] = useState(initialDraft);
  return (
    <div>
      <p className="ai-notice">AI draft — review and edit before sending</p>
      <textarea value={value} onChange={(e) => setValue(e.target.value)} />
      <button onClick={() => onSend(value)}>Send</button>
    </div>
  );
}

// components/StreamingText.tsx — cursor while active, disclosure once complete
function StreamingText({ text, loading }: { text: string; loading: boolean }) {
  return (
    <div aria-live="polite">
      <p className="streaming-text">
        {text}
        {loading && <span className="cursor" aria-hidden="true">▋</span>}
      </p>
      {!loading && text && <AiOutput content="" source="ai" />}
      {text.includes("I'm not sure") && <p className="ai-caveat">AI flagged uncertainty — verify this output.</p>}
    </div>
  );
}

// components/ErrorBanner.tsx — specific, actionable, screen-reader announced
const AI_ERRORS: Record<string, string> = {
  unavailable: 'AI is temporarily unavailable. Please try again in a moment.',
  too_long: 'The text is too long. Please shorten it and try again.',
  content_policy: 'This content cannot be processed. Please rephrase your request.',
};

function ErrorBanner({ code }: { code: string }) {
  return <div role="alert" className="error-banner">{AI_ERRORS[code] ?? AI_ERRORS.unavailable}</div>;
}
```

## When to Use
- Any surface that displays AI-generated text, images, or recommendations directly to a user
- Any AI-initiated draft that will become an email, message, comment, or form submission — the editable-draft pattern applies before any of these ever get sent
- Chat interfaces and any streaming response, where the loading/cursor/completion sequence needs to be consistent across the product
- Whenever designing error states for an AI feature — build the code-to-message map at the same time as the happy path, not after
- Accessibility review of any AI feature before launch — loading, streaming, and error states each need their own pass

## Common Mistakes
- Rendering AI output with no disclosure label, or a label small enough to require scrolling to notice
- Auto-submitting an AI-generated email, form, or message without a user review step
- Showing a blank area or a generic spinner with no context while an AI call is in flight for several seconds
- Using one generic "something went wrong" message for every AI failure instead of mapping error codes to specific, actionable text
- Suppressing a model's own expressed uncertainty because it makes the output look less polished
