# 465. The Viewer Is a Client of Your Data, Not the Source of Truth

## What It Is
**Mode: cloud.** The Viewer is a JavaScript component that renders a translated derivative in a browser, with selection, sectioning, measurement and a property panel. It is genuinely good, and it invites an architectural mistake that is expensive to undo.

The mistake is letting the Viewer become where data lives. It renders a derivative, so it knows what the derivative carries; it does not know your asset register, your work orders, your survey results or anything else your application is actually about. Once business logic starts reading values out of the property panel and writing state into Viewer extensions, the derivative has quietly become the database — a database you cannot query, cannot migrate, cannot back up, and which is regenerated wholesale every time someone re-translates a model.

The shape that works inverts it. **Your system owns the data; the Viewer is one client of it.** A selection in the Viewer produces an object id; you resolve that to your own record and answer from your own store. State the user creates is written to your API, not into the scene. The Viewer's job is to draw geometry and report interaction, and it is very good at exactly that.

This also settles two recurring questions. Property values shown in the panel are the derivative's, which per Lesson 464 is a translation output rather than the model — so a value that has to be authoritative comes from your system, displayed alongside. And an object id from a selection is a handle for this derivative, so resolving it to a durable key is a step you have to do rather than one you can skip.

## Key Concepts
- **The Viewer renders a derivative** — geometry, selection, sectioning, measurement, a property panel
- **It knows the derivative and nothing else** — not your records, not your workflow, not your history
- **Your system owns the data; the Viewer is a client** — the inversion that keeps the architecture workable
- **Selection produces an object id**, which Lesson 464 established is derivative-scoped
- **Resolve to a durable key** before doing anything with a selection
- **State goes to your API, not into the scene** — a scene is regenerated by the next translation
- **The property panel is display, not authority** — an authoritative value is displayed *alongside* it, from your store
- **Tokens for the browser are minted narrow**, per Lesson 461 — a viewer needs read access to one derivative

## Example Code
The boundary, written as a function so it is somewhere rather than everywhere:

```typescript
/** What the Viewer can tell you: an id in this derivative, and nothing else.
 *  Typed here rather than imported, because the boundary is the point — the
 *  moment a Viewer type appears in application code, the boundary is gone. */
type ViewerSelection = { urn: string; objectIds: readonly number[] };

/** What your system understands. The durable key is the shared parameter GUID
 *  from Lesson 459, carried through the derivative as a property. */
type AssetRef = { assetTag: string };

type PropertyLookup = (urn: string, objectId: number) => Promise<string | null>;

/** One place where a selection becomes a business reference. Everything after
 *  this function talks about assets; nothing after it mentions object ids. */
export async function toAssetRefs(
  selection: ViewerSelection,
  readAssetTag: PropertyLookup
): Promise<{ resolved: AssetRef[]; unresolved: number[] }> {
  const resolved: AssetRef[] = [];
  const unresolved: number[] = [];
  for (const objectId of selection.objectIds) {
    const tag = await readAssetTag(selection.urn, objectId);
    // An element with no asset tag is a real answer, not an error: plenty of
    // geometry is not an asset. Reporting it as unresolved is how the gap
    // becomes visible instead of becoming a silent drop.
    if (tag === null) unresolved.push(objectId);
    else resolved.push({ assetTag: tag });
  }
  return { resolved, unresolved };
}
```

## When to Use
- Any application where people need to see a model alongside data that is not in the model
- When the Viewer is one of several clients — a mobile view, a report, an API — and the data has to be the same in all of them
- When designing the selection boundary, which is the one place object ids should appear
- When deciding what a token handed to the browser may do, where Lesson 461's narrow-and-short-lived rule applies directly

## Common Mistakes
- **Reading business values out of the property panel** — those are the derivative's values, and the derivative is a translation output
- **Storing application state in the scene or in a Viewer extension** — the next translation regenerates the derivative and the state is gone
- **Using object ids as foreign keys** — derivative-scoped, per Lesson 464, so the join breaks on re-translation without an error
- **Letting Viewer types spread through application code** — once they are everywhere, the Viewer is no longer replaceable and neither is the derivative
- **Giving the browser a broad token** — it needs read access to one derivative, and anything wider is now in the client
- **Treating the Viewer as the product** — it draws geometry extremely well, and the product is what your system knows that the model does not
