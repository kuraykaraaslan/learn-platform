# 331. Building a Productized Offer Catalog with Real Price Bands

## What It Is
> This lesson is general education, not financial or tax advice. Price bands shown here are illustrative examples — validate your own pricing against your market, cost base, and actual delivery hours.

A productized service turns repeated freelance work into something easier to buy, sell, and deliver — without becoming fully custom again. It doesn't eliminate customization; it bounds it. A landing page package that flexes on colors and copy but always delivers six fixed sections, a contact form, and analytics setup is productized. A landing page package that might become a five-page site, might include a CMS, and might need a client portal depending on the conversation is not — it's a custom project wearing a productized label.

Every entry in a real offer catalog needs the same structure: a clear problem it solves, an ideal buyer, defined input requirements, fixed or tightly bounded deliverables, a repeatable process, a realistic timeline range, clear price logic, explicit exclusions, and a next-step upgrade path. A catalog built this way reads like a menu: a prospect can self-select the right package from the problem description alone, without a scoping call to understand what they'd even be buying.

The catalog should launch small and prove itself before expanding — one clear offer, one page describing it, one intake form, one delivery template, and one follow-up path is enough to start selling. Overbuilding the catalog before the first sale is a common trap; better to sell one productized package five times and refine it than to launch five packages that have never been tested against a real buyer.

## Key Concepts
- **Required elements per offer**: clear problem, ideal buyer, input requirements, fixed or bounded deliverables, process steps, timeline range, price logic, exclusions, upgrade path.
- **Service page formula**: Who This Is For, Problem, Outcome, What You Get, Process, What Is Not Included, Next Step — a consistent structure across every catalog entry.
- **Start small rule**: launch with one offer, one page, one intake form, one delivery template, one follow-up path — expand only after it sells.
- **Bounded customization**: the package can adapt to the client's specifics, but the deliverable shape stays fixed — e.g., "the audit adapts to your system, but the output is always a report, a risk matrix, and a roadmap."
- **Upgrade paths**: every productized offer should point somewhere — an MVP Scope Blueprint leads to an MVP Build, a Codebase Review leads to a Refactor Sprint or a maintenance retainer.
- **Forbidden patterns**: calling a fully custom project "productized," promising a fixed outcome without fixed inputs, including unlimited meetings or revisions, and selling a package with no defined next-step offer.

## Example Code
A catalog entry written to the service-page formula, with a defined price band:

```md
# Admin Panel Starter Sprint

## Who This Is For
Businesses running core operations in spreadsheets who need one shared,
role-based internal tool.

## Problem
Data lives in disconnected spreadsheets; multiple people edit the same
file; there is no audit trail of who changed what.

## Outcome
A working internal admin panel with authentication, roles, and the top
5 data entities the team actually manages daily.

## What You Get
- Auth with 2-3 user roles
- Up to 5 core data entities (CRUD)
- Dashboard with key metrics
- CSV/Excel data import
- Deployment + 1 training session

## Process
1. Data modeling workshop (defines entities, roles, relationships)
2. Backend build
3. UI/dashboard build
4. Client UAT
5. Deployment + handover

## What Is Not Included
- Mobile app, complex reporting/BI, third-party integrations,
  more than 5 entities, ongoing feature development

## Next Step
A Maintenance or Improvement Retainer to extend the panel after launch.

Price band: $15,000-$28,000 depending on entity complexity. Timeline: 6 weeks.
```
The price band and exclusions are visible before a single call happens — a prospect with 15 entity types self-identifies as out of scope before wasting anyone's time.

## When to Use
- When the same type of project keeps getting quoted from scratch each time — a signal it's ready to become a catalog entry.
- When building a website, proposal template, or sales page that should let prospects self-qualify before a call.
- When trying to reduce the number of scoping calls needed to close a standard project type.
- When reviewing an existing offer that keeps scope-creeping — check whether its exclusions are actually written down anywhere.

## Common Mistakes
- Building an elaborate multi-package catalog before a single package has been sold and refined against real client feedback.
- Leaving exclusions unwritten, so "not included" becomes a negotiation instead of a stated boundary.
- Promising a fixed outcome (e.g., "SEO ranking improvement") without fixed inputs the client must provide.
- Launching a productized offer with no upgrade path, leaving satisfied clients with nowhere obvious to go next.
