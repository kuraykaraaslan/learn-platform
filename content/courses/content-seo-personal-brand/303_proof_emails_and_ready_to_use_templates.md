## What It Is
Proof emails exist to help a prospect trust the freelancer before a sales call ever happens, and the thing that makes one work is showing the thinking behind the work rather than just announcing that a project got completed. The six-part structure — context, problem, constraint, approach, result or learning, and a soft CTA — turns "I built a booking system" into something a reader can actually learn from: a common pattern in SMEs where the real business process lives in spreadsheets and WhatsApp messages, the decision to separate version one from the roadmap, and the lesson that screens are easy to imagine but approvals, exceptions, roles, and data rules define the real scope. That gap between weak and strong proof is almost entirely about specificity. "I built a modern app using React and Node.js" says nothing a reader can use. "The project replaced a manual request-tracking workflow with role-based submission, approval, status tracking, and exportable reports; the technical challenge was keeping the first version small while leaving room for future automation" says exactly what problem was solved and what judgment was required to solve it.

Confidentiality runs underneath every proof email as a non-negotiable constraint, not a stylistic choice — client names, private data, credentials, internal screenshots, and commercially sensitive workflows never appear without explicit permission, and generic descriptions ("a regional operations company," "a B2B service provider") do the same trust-building job without the risk. Proof doesn't have to come only from full case studies, either: an architecture note, a technical decision explanation, a bug or risk avoided, a performance or security improvement, a handover example, or a client testimonial can all carry a proof email on their own, which matters for a solo practice that doesn't finish a flagship case study every month.

Templates exist to remove the blank-page problem for recurring email types, not to replace judgment — a newsletter issue, a lead magnet delivery, an MVP nurture email, a workflow automation email, a case study email, a soft sales invitation, and a past-client check-in cover most of what a freelance software business actually needs to send on a repeating basis. But a template is a starting skeleton, not finished copy: audience, problem, example, CTA, service relevance, and confidentiality all need to be adapted before sending, and the reader should never be able to tell they received something assembled from a generic funnel rather than written for them specifically. Sending a template unmodified is the fastest way to turn a system meant to save time into a system that quietly damages the trust the rest of the email program spent months building.

## Key Concepts
- **Six-part proof email structure**: context → problem → constraint → approach → result or learning → relevance to the reader → soft CTA.
- **Weak vs. strong proof language**: generic tech-stack claims ("built a modern app") prove nothing; specific workflow and constraint language proves judgment was actually exercised.
- **Confidentiality is non-negotiable, not stylistic**: client names, private data, credentials, and sensitive workflows require explicit permission or must be generalized into safe categories.
- **Proof beyond case studies**: architecture notes, avoided risks, performance/security improvements, handover examples, and testimonials are all legitimate proof-email content on their own.
- **Seven core templates**: newsletter issue, lead magnet delivery, MVP nurture, workflow automation, case study, soft sales invitation, and past-client check-in cover most recurring email needs.
- **Templates are accelerators, not finished copy**: every send requires customizing audience, problem, example, CTA, service relevance, and confidentiality before it goes out.
- **The "does this feel generic" test**: the reader should never sense they received unmodified funnel copy — a template used well is invisible as a template.

## Example Code
```md
## Sanitized Proof Email Template

Subject: How a manual workflow becomes an admin panel

A common pattern I see in SMEs: the real business process lives in
spreadsheets, WhatsApp messages, and memory.

In one project, the first useful version was not a huge platform. It was a
focused internal system for <workflow>, with <roles>, <core actions>, and
<reporting/output>.

The important decision was separating version one from the roadmap. We kept
<must-have> and postponed <nice-to-have>.

The lesson: before asking for a development estimate, map the workflow.
Screens are easy to imagine, but approvals, exceptions, roles, and data
rules define the real scope.

If you are trying to turn a manual process into software, reply with the
workflow and I can tell you what I would clarify first.

## Template Customization Checklist (run before every send)

[ ] Audience matches this specific recipient/segment
[ ] Problem is the reader's actual problem, not a generic placeholder
[ ] Example is concrete, not abstract
[ ] CTA matches this reader's stage
[ ] Service relevance is explicit
[ ] Confidentiality check passed (no unapproved names/data)
```

## When to Use
- Preparing a proof email ahead of a sales conversation, to build trust before the call happens
- Templating a recurring email type (check-ins, lead magnet delivery) to save writing time without losing quality
- Reviewing a draft that leans on generic tech-stack language instead of the actual workflow or constraint
- Deciding which proof type to use when a full case study isn't ready yet but a smaller proof point is
- Right before sending any templated email, as a final customization gate

## Common Mistakes
- Naming a client or exposing private data in a proof email without explicit permission
- Using generic language ("modern, scalable app") instead of the concrete workflow and constraint that was actually solved
- Sending a template unmodified, so the recipient can tell it was assembled rather than written for them
- Treating a completed project as good for only one proof email instead of extracting the sharpest lesson from it
- Skipping the confidentiality check because the deadline is close and the email "just needs to go out"
