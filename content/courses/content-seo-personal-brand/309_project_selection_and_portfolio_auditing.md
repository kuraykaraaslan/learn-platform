## What It Is
A portfolio shouldn't contain everything — it should contain the projects that support the freelancer's positioning and help the right client trust them faster, which means selection has to be strategic rather than chronological. A project earns a spot only if it proves at least one commercially useful capability: business workflow understanding, product scoping, technical architecture, UI/UX execution, backend or API design, integration work, security awareness, deployment ownership, or client communication. A visually nice project that proves none of these doesn't belong, no matter how much effort went into it. The selection score makes this concrete: each candidate gets rated 0–25 across five categories — buyer relevance, problem clarity, proof quality, technical depth, and differentiation — and the total maps directly to a format decision: 20–25 becomes a full case study, 15–19 a shorter portfolio item, 10–14 gets used only as a social post or technical note, and 0–9 doesn't get included unless there's a specific strategic reason to make an exception.

A strong solo portfolio isn't just a pile of high-scoring projects, though — it needs a deliberate mix: one flagship case study, two to three detailed case studies, three to six shorter project cards, one technical architecture breakdown, one UI or demo-heavy project, one business or process automation example, and one experimental or open-source proof item. This mix matters because different buyers are looking for proof of different capabilities, and a portfolio that's all SaaS MVPs, for instance, says nothing to a prospect specifically looking for admin panel or automation proof. Exclusion criteria matter as much as inclusion: projects that are too trivial, look unfinished, conflict with current positioning, can't be explained clearly, have no available proof assets, or create a confidentiality risk should be left out — and if an older, lower-quality project is still strategically important to show, it's usually better reframed as a "before I improved my process" lesson than presented as current best work.

Selection decides what goes into the portfolio; auditing is the separate, ongoing discipline of reviewing what's already there. The question an audit asks isn't "does this look nice?" — it's "does this make the right client trust me enough to start a conversation?" Every visible item gets scored 0–5 across seven dimensions: positioning, problem clarity, solution clarity, technical proof, visual proof, result clarity, and CTA strength, for a total out of 35. A score of 30–35 means feature the item prominently; 22–29 means improve and keep it; 15–21 means it only belongs as a short card, not a full case study; 0–14 means remove or archive it. The same audit extends to the page level — are the strongest projects above the fold, can visitors filter by project type, does each card explain outcome rather than just stack, is there a clear CTA, does the page load quickly and work on mobile — because a strong individual case study can still underperform sitting on a poorly structured page. Common fixes for a weak case study are specific and repeatable: add problem context, add a before-after section, add technical decision notes, add captioned screenshots, add a result statement, add a CTA, remove irrelevant stack lists, and anonymize any risky details that shouldn't be public.

## Key Concepts
- **Portfolio-worthy capability list**: a project must prove at least one commercially useful capability — workflow understanding, architecture, UI/UX, integration, deployment ownership, or client communication — not just look good.
- **Selection score (0–25)**: buyer relevance, problem clarity, proof quality, technical depth, and differentiation, mapped to a decision threshold (full case study / short item / social post / exclude).
- **Deliberate portfolio mix**: one flagship, 2–3 detailed case studies, 3–6 short cards, plus specific category coverage (SaaS/MVP, admin/dashboard, integration, e-commerce, infrastructure, UI system).
- **Exclusion criteria**: too trivial, unfinished-looking, conflicts with current positioning, no proof assets, or confidentiality risk — none of these are worth the space regardless of effort invested.
- **Reframing old work honestly**: a lower-quality older project can still be shown, reframed explicitly as a "before I improved my process" lesson rather than current best work.
- **Portfolio item audit score (0–35)**: seven dimensions at 0–5 each — positioning, problem, solution, technical proof, visual proof, result, and CTA — mapped to feature / improve / short-card / remove.
- **Page-level audit layered on item-level audit**: above-the-fold strength, filterability, mobile performance, and load speed all matter even when individual case studies score well.
- **Repeatable fixes for a weak item**: add problem context, add before-after, add technical decision notes, add captions, add a result statement, add a CTA, remove stack-only lists, anonymize risky details.

## Example Code
```md
## Project Selection Score

| Category          | 0 pts          | 3 pts             | 5 pts                          |
|--------------------|----------------|--------------------|----------------------------------|
| Buyer relevance     | No clear buyer | Some relevance      | Strong ICP match                 |
| Problem clarity     | No problem     | Generic problem     | Clear, painful problem           |
| Proof quality       | No assets      | Some screenshots     | Demo + screenshots + metrics     |
| Technical depth     | Basic          | Some depth           | Strong architecture decisions    |
| Differentiation     | Common work    | Some uniqueness      | Distinct expertise shown         |

Score: __ / 25
20–25 → Full case study   15–19 → Short item
10–14 → Social post only  0–9   → Exclude

## Portfolio Item Audit

| Dimension        | 0–5 | Question                                          |
|-------------------|----:|-----------------------------------------------------|
| Positioning        |     | Does this support the work I want more of?          |
| Problem            |     | Is the original problem clear?                       |
| Solution           |     | Is the delivered solution understandable?             |
| Technical proof     |     | Are decisions/trade-offs credible?                    |
| Visual proof        |     | Are screenshots/demo/diagrams useful?                 |
| Result             |     | Is the outcome or intended value clear?                |
| CTA                |     | Does the reader know what to do next?                  |

Total: __ / 35
30–35 → Feature   22–29 → Improve   15–21 → Short card only   0–14 → Remove
```

## When to Use
- Deciding whether a just-finished project deserves a full case study, a short card, or nothing at all
- Running a quarterly or pre-launch portfolio review
- When the portfolio feels cluttered or the strongest work is buried below weaker items
- Repositioning the business and needing to know which old projects still fit the new direction
- When a specific buyer type (e.g., agency partners) has no representative project proving relevant capability

## Common Mistakes
- Including a project because it's recent or uses trendy technology rather than because it proves a buyer-relevant capability
- Keeping every project "just in case" instead of applying the exclusion criteria honestly
- Letting the strongest case study sit below weaker items instead of featuring it prominently
- Never re-auditing the portfolio after the initial launch, so it drifts out of sync with current positioning
- Presenting an outdated, lower-quality project as current best work instead of reframing it as a lesson
