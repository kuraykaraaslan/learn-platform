# 313. Proof Asset Repurposing — One Case Study, Many Assets

## What It Is
A single strong project should never live only as one portfolio page — the discipline is treating every full case study as raw material for at least five distinct trust assets: the portfolio page itself, a LinkedIn post, a technical blog or note, a short demo video, and a proposal proof snippet, with a carousel, newsletter mention, GitHub README, architecture diagram, or sales-email proof block available as optional extensions. This isn't about stretching one idea thin — it's about recognizing that a well-built case study already contains enough distinct material (a problem, a before/after, a technical decision, a constraint, a lesson) that each piece can stand on its own in a different format for a different reader who will never encounter the others.

The repurposing map makes the mapping explicit rather than something to figure out fresh each time: the problem section becomes a LinkedIn problem-focused post, the before/after becomes a carousel or short video, the technical approach becomes a blog post or GitHub README, the result becomes a testimonial or proposal snippet, the constraints become a thought-leadership post about real-world trade-offs, and the lessons learned become a newsletter issue. Each downstream format has its own compressed shape — a LinkedIn mini-case, for instance, follows a specific arc: name a common mistake, describe the real issue behind a recent project's before-state, explain the scoping decision that kept things realistic, add a short technical proof point, and close with the lesson. A proposal proof snippet does something slightly different: it reuses the same case study to speak directly to a live prospect's specific situation — "this is similar to your situation because..." — turning a finished asset into fast, credible proof under proposal deadline pressure instead of writing something new from scratch every time.

None of this works on a dump-everything-at-once schedule; a realistic cadence spreads one case study across roughly a month — publish the portfolio page and a LinkedIn announcement in week one, a technical breakdown post in week two, a short demo video in week three, and a lessons-learned post in week four — with the finished case study then held in reserve to support future proposals and discovery follow-ups indefinitely. And every discipline that governed the original case study travels forward into every repurposed asset: no copying the same paragraph verbatim into three different formats and calling it repurposing, no reusing one screenshot without fresh context, no turning every repurposed piece into a hard pitch, and no relaxing the confidentiality rules just because the format changed — a detail too sensitive for the case study is exactly as sensitive in a "quick" LinkedIn post built from the same material.

## Key Concepts
- **One case study, five-plus assets minimum**: portfolio page, LinkedIn post, technical blog/note, short demo video, and proposal proof snippet — carousel, newsletter, GitHub README, and architecture diagram as optional extensions.
- **Repurposing map**: problem → LinkedIn post, before/after → carousel/video, technical approach → blog/README, result → testimonial/proposal snippet, constraints → thought-leadership post, lessons learned → newsletter.
- **LinkedIn mini-case arc**: common mistake → real before-state issue → scoping decision → short technical proof → lesson, compressed into a few short paragraphs.
- **Proposal proof snippet**: reuses an existing case study to speak directly to a live prospect's specific situation, producing fast, credible proof under deadline pressure.
- **A month-long rollout cadence**: portfolio page + LinkedIn announcement (week 1), technical breakdown (week 2), demo video (week 3), lessons-learned post (week 4), then held in reserve for future proposals.
- **Confidentiality travels with the content**: a detail too sensitive for the original case study is exactly as sensitive in any repurposed version of it, regardless of format or urgency.
- **No verbatim duplication across formats**: each asset should be adapted to its format and reader, not copy-pasted from the source case study.

## Example Code
```md
## Repurposing Map (source: a completed appointment booking project)

| Source section         | Repurpose into                          |
|--------------------------|-------------------------------------------|
| Problem                   | LinkedIn problem-focused post              |
| Before/after              | Carousel or short video                    |
| Technical approach         | Blog post or GitHub README                 |
| Result                    | Testimonial/proposal snippet               |
| Constraints                | Thought-leadership post                    |
| Lessons learned            | Newsletter issue                           |

## LinkedIn Mini-Case Template

A common mistake in custom software projects: jumping to features before
mapping the workflow.

In a recent <project type>, the real issue was not the UI. The team was
dealing with <before-state>.

The first version focused only on <core workflow>. That decision kept the
scope realistic and made the system useful faster.

The technical side included <short technical proof>.

Lesson: <principle>.

## 4-Week Rollout Cadence

Week 1: publish portfolio page + LinkedIn announcement
Week 2: technical breakdown post
Week 3: short demo video
Week 4: lessons-learned post
Later:  reuse in proposals and discovery follow-ups
```

## When to Use
- Immediately after a case study is finished and published, while it's still fresh
- When the content calendar is running dry and a recent project hasn't been mined for assets yet
- Preparing proposal proof for an active prospect whose situation resembles a past project
- Deciding how to spread one significant project across a month of content instead of one post
- Reviewing whether a finished case study is being left to sit as a single, underused asset

## Common Mistakes
- **A case study gets published once and never turned into anything else** — Publishing the case study once and never revisiting it for any other format
- **The exact same paragraph gets pasted into LinkedIn, the newsletter, and a proposal** — Copy-pasting the same paragraph into LinkedIn, the newsletter, and a proposal with no adaptation
- **A quick repurposed post mentions a detail the original case study's review would have caught** — Leaking a confidential detail in a "quick" repurposed post that would never have survived review in the original case study
- **The same screenshot shows up in three different repurposed assets, same caption each time** — Reusing the same screenshot across multiple assets with no fresh context or caption
- **A full month's worth of repurposed content gets published in a single week** — Dumping the entire repurposing plan into a single week instead of pacing it across a month
