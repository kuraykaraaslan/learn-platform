# 406. Spring Boot: Service Layer Beans and @Transactional Scoping

## What It Is
A Spring Boot `@Service` is a container-managed bean, not a static class called directly — and that distinction is the whole reason `@Transactional` works. Spring implements `@Transactional` (and `@PreAuthorize`, and most other declarative behavior) using a runtime proxy that wraps the bean: when another bean calls a `@Transactional` method through the injected reference, the call actually goes through the proxy first, which opens a transaction, invokes the real method, and commits or rolls back afterward. A `static` method, or a call from *within the same class* to one of its own `@Transactional` methods, bypasses this proxy entirely — the annotation is present in the source but has no effect at runtime. This single mechanism explains three of the most common "why doesn't this work" moments for anyone arriving from Express, where services are plain static classes with no proxy in the picture at all.

Transaction scoping follows a simple rule once the proxy mechanism is understood: annotate write operations (insert/update/delete) with `@Transactional`, annotate read operations with `@Transactional(readOnly = true)` (which lets Hibernate skip dirty-checking and can route to read replicas), and leave orchestration methods that only call other already-`@Transactional` services unannotated — the inner methods each manage their own transaction, and wrapping them in an outer transaction just inflates its duration without adding safety, unless true cross-call atomicity is required.

Dependency wiring is constructor injection only, generated by Lombok's `@RequiredArgsConstructor` from `final` fields — field injection via `@Autowired` is banned because it hides a bean's dependencies from its constructor signature and makes it awkward to instantiate in a plain unit test. And services are throw-only: a Spring Boot service signals failure by throwing `AppException`, never by returning `null`, a boolean, or an `Optional` at the service boundary (an `Optional` returned from a *repository* method inside the service is fine — it just has to be resolved to a throw before the service method returns).

## Key Concepts
- **`@Service` is a proxied Spring bean**: `@Transactional`, `@PreAuthorize`, and other AOP-based annotations only take effect on calls made *through* the proxy — i.e., calls from another injected bean
- **Constructor injection via `@RequiredArgsConstructor`**: never `@Autowired` field injection; dependencies are `private final` fields
- **`@Transactional` on writes, `@Transactional(readOnly = true)` on reads**: the `readOnly` flag enables Hibernate optimizations and documents intent
- **No annotation on pure orchestration**: a method that only calls other already-`@Transactional` services needs no annotation of its own — add one only when true atomicity across those calls is required
- **Self-invocation defeats the proxy**: calling `this.someTransactionalMethod()` from within the same class does not go through the proxy — split the call into a separate injected bean if the transactional behavior must apply
- **Service interface is optional**: don't create a `UserService`/`UserServiceImpl` pair unless there are genuinely multiple implementations, or a framework contract (like Spring Security's `UserDetailsService`) requires it
- **Method naming convention**: `getBy[Field]`, `list[Resource]`, `create[Resource]`, `update[Resource]`, `patch[Resource]`, `delete[Resource]`, `exists[Condition]` — never generic names like `process` or `handle`
- **Throw, never return null/Optional at the boundary**: `userRepository.findById(id).orElseThrow(() -> new AppException(...))` is the standard shape

## Example Code
```java
// modules/order/service/OrderService.java
@Service
@RequiredArgsConstructor
@Slf4j
public class OrderService {

    private final OrderRepository orderRepository;
    private final PaymentService paymentService;
    private final NotificationService notificationService;

    // ✅ Write — explicit @Transactional
    @Transactional
    public OrderResponse createOrder(UUID tenantId, CreateOrderRequest request) {
        OrderEntity order = OrderEntity.builder()
            .tenantId(tenantId)
            .status(OrderStatus.PENDING)
            .total(request.total())
            .build();
        return OrderResponse.from(orderRepository.save(order));
    }

    // ✅ Read — readOnly enables Hibernate dirty-check skip
    @Transactional(readOnly = true)
    public OrderResponse getById(UUID orderId) {
        return OrderResponse.from(
            orderRepository.findById(orderId)
                .orElseThrow(() -> new AppException(OrderMessages.ORDER_NOT_FOUND, 404))
        );
    }

    // ✅ Orchestration — no annotation; each inner call manages its own transaction
    public void processOrder(UUID orderId) {
        paymentService.charge(orderId);          // @Transactional inside PaymentService
        markOrderPaid(orderId);                  // @Transactional inside this class
        notificationService.notifyPaid(orderId); // fire-and-forget, non-transactional
    }

    @Transactional
    public void markOrderPaid(UUID orderId) {
        OrderEntity order = orderRepository.findById(orderId)
            .orElseThrow(() -> new AppException(OrderMessages.ORDER_NOT_FOUND, 404));
        order.setStatus(OrderStatus.PAID);
        orderRepository.save(order);
    }
}

// ❌ Self-invocation — markAllPaid() calling this.markOrderPaid() bypasses the proxy
@Service
public class BrokenOrderService {
    public void markAllPaid(List<UUID> orderIds) {
        orderIds.forEach(this::markOrderPaid);   // ← @Transactional on markOrderPaid is NOT applied
    }

    @Transactional
    public void markOrderPaid(UUID orderId) { /* ... */ }
}

// ✅ Fix — move the loop to a separate bean so the call goes through the proxy
@Service
@RequiredArgsConstructor
public class OrderBatchService {
    private final OrderService orderService;

    public void markAllPaid(List<UUID> orderIds) {
        orderIds.forEach(orderService::markOrderPaid);  // ← calls the real proxy
    }
}
```

## When to Use
- Writing any `@Service` — default to constructor injection and decide the `@Transactional` scoping (write, read-only, or none) before writing the method body
- Porting an Express static-service module to Spring Boot — every `static async` method becomes an instance method on an injected, `@Transactional`-annotated bean
- A method loops and calls another `@Transactional` method on the same class — stop and move the looped call into a separate bean so the proxy actually applies
- Deciding whether a service needs an interface — only when a second implementation genuinely exists, or a Spring contract requires one

## Common Mistakes
- **Copying Express's static-class service pattern** — `public static UserResponse getById(...)` bypasses the Spring proxy entirely; `@Transactional` on a static method has no effect.
- **Self-invocation of `@Transactional` methods** — calling `this.method()` from within the same class silently skips the proxy; split the caller and callee into separate beans.
- **`@Transactional` on an orchestration method that only calls other transactional services** — this inflates the outer transaction's duration for no correctness benefit; omit it unless true cross-call atomicity is required.
- **Field injection with `@Autowired`** — hides the bean's real dependencies and makes plain (non-Spring) unit testing awkward; use `@RequiredArgsConstructor` instead.
- **Returning `Optional<T>` or `null` from a service method to signal "not found"** — throw `AppException` instead; `Optional` is acceptable only as a repository return type resolved via `.orElseThrow()` inside the service.
