# 475. Idempotent Ingest: Deduplicating a Reading That Arrives Three Times

## What It Is
Lesson 469 established that duplication on this path is normal rather than exceptional. This lesson is about where you handle it, and the answer is a constraint in the database rather than logic in the ingest.

Three ordinary things produce duplicates, and **none of them is a fault**. An acknowledgement gets lost, so the sender retries a delivery that actually succeeded. Two gateways are in range of one transmitter and both forward what they heard. A device that buffered through an outage flushes its backlog, including the last reading it had already delivered before the link dropped. A correctly working network produces all three.

The fix is to decide what a reading's **identity** is, and it is the pair `(device, measurement time)` — plus the metric, if one row holds several. That is the key that is the same across every copy of one reading and different across two genuinely different readings. The tempting alternatives both fail: **arrival time** differs between copies of the same reading, so it deduplicates nothing; **measurement time alone** is shared by two devices that happened to sample at the same instant, so it deletes real data.

With the key chosen, the mechanism is a unique constraint and `ON CONFLICT DO NOTHING`. This is better than a check-then-insert in the application for the usual reason — the check and the insert are not atomic, so two concurrent copies of one reading can both pass the check — and better than deduplicating in a stream processor because the constraint holds regardless of which path a row arrives by, including a backfill someone runs by hand at midnight.

The general pattern is the one (#7) sets out; what differs here is the key. An HTTP idempotency key is generated by the client for one request. A reading's key is **intrinsic** — it is derivable from the reading itself, by anyone, at any point on the path — which is stronger, and it is available because a measurement genuinely is identified by what measured it and when.

## Key Concepts
- **Duplicates are routine**: lost acknowledgement, second gateway, backlog flush — none is a fault
- **Identity is `(device, metric, measurement time)`** — the same across copies, different across readings
- **Arrival time deduplicates nothing**: copies arrive at different times
- **Measurement time alone deletes data**: two devices can sample at one instant
- **A unique constraint plus `ON CONFLICT DO NOTHING`** is the mechanism
- **Better than check-then-insert**: those are not atomic, so concurrent copies both pass
- **Better than deduplicating in the stream**: the constraint holds for every write path, including manual backfills
- **An intrinsic key beats a generated one** — derivable by anyone, anywhere on the path, unlike (#7)'s client-generated key
- **A duplicate is a success**: acknowledge it, or the sender retries what it already delivered (Lesson 471)

And the same thing against real Postgres. The seed holds 612 arrivals of 480 distinct readings, with the duplicates injected by cause:

```sql run seed=sensor_readings
-- What the transport actually delivered, by cause. Nothing here failed:
-- every one of these arrivals is a correct thing for the network to have done.
SELECT cause, count(*) AS arrivals
FROM reading_arrival
GROUP BY cause
ORDER BY arrivals DESC;
```

```sql run seed=sensor_readings
-- The naive ingest: every arrival becomes a row. It runs, it is fast, and it
-- is wrong in a way no error reports.
INSERT INTO sensor_reading (device_id, measured_at, celsius)
SELECT device_id, measured_at, celsius FROM reading_arrival
ON CONFLICT (device_id, measured_at) DO NOTHING;

-- How many arrivals there were, and how many readings actually exist.
SELECT
  (SELECT count(*) FROM reading_arrival) AS arrivals,
  (SELECT count(*) FROM sensor_reading)  AS stored,
  (SELECT count(*) FROM reading_arrival) - (SELECT count(*) FROM sensor_reading) AS dropped_as_duplicate;
```

The constraint did the work. No application code inspected anything, and the same protection applies to a backfill script, a replay from an archive, and a second ingest process nobody remembered to tell.

```sql run seed=sensor_readings
-- What the duplicates would have done to a report, had the constraint not
-- been there. Same question, asked of the raw arrivals and of the readings.
SELECT
  round(avg(celsius), 4) AS mean_from_arrivals,
  count(*)               AS rows_counted
FROM reading_arrival
WHERE device_id = 'dev-0003';

SELECT
  round(avg(celsius), 4) AS mean_from_readings,
  count(*)               AS rows_counted
FROM sensor_reading
WHERE device_id = 'dev-0003';
```

The means differ. Neither row is wrong on its own; the duplicated readings are simply counted more than once, and only the answer is affected.

## When to Use
- Every telemetry ingest, without exception — the duplicates arrive whether or not you planned for them
- When designing the table, since the key is a primary key decision and retrofitting one over duplicated data is a migration
- When a report disagrees with a device's own count, where a duplicate count is the first thing to check
- Alongside (#7)'s pattern when an HTTP path also writes readings, so both paths land on the same constraint

## Common Mistakes
- **Deduplicating in the application** — check-then-insert is not atomic, and two concurrent copies both pass the check
- **Deduplicating in the stream processor only** — a backfill, a replay or a second writer bypasses it, and the constraint would not have been bypassed
- **Keying on arrival time** — it differs between copies, so it deduplicates nothing at all
- **Keying on measurement time alone** — two devices sampling at one instant collide, and the fix deletes real readings
- **Returning an error for a duplicate** — the sender reads it as a failed delivery and retries, so one duplicate becomes a loop (Lesson 471)
- **Assuming the transport will stop duplicating** — two gateways hearing one uplink is the network working, and no configuration removes it
